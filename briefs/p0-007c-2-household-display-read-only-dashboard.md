## Why

The household now has an actionable personal Today and summarized oversight. The next useful result is a dining-room display that stays enrolled, shows the actual family day, and can be inspected from across the room. That requires a household-owned device identity with restricted data access as well as a readable layout.

This is the **second of three slices** of Design's revised P0-007C proposal. C-1 is integrated. C-2 delivers enrollment, revocation and a live **read-only** wall. C-3 will add normal assigned checklist execution with truthful display provenance and owner-controlled personal-work promotion. Reading checklists here does not authorize completing them, and this slice alone does not finish the full Product outcome.

## Learning question

Can six people understand ownership and progress from the dining-room table, then walk up and inspect one person's work, while the device remains reliably enrolled and private information stays out of its responses?

## Player experience

A manager opens **Household displays**, names a display and gets a temporary setup code. In a separate, signed-out browser on the wall, they open **Set up Household Dashboard** and enter that code. The wall opens By person, with six friendly names, meaningful progress, major unfinished work and the household date/time. By work answers who owns Kitchen or Cats and who has finished a routine. Tapping opens a large read-only detail; Back or an idle interval returns to the overview.

Phone activity updates the wall. Closing/reopening its normal browser or restarting the server preserves enrollment. The manager can revoke or replace that display from their own device. The wall offers neither normal administration nor private personal work.

## Behavioral contract

### 1. A household device, with explicit management authority

- Add a stable **Household Display** identity belonging to exactly one household. Store its friendly label, creator membership, created/revoked facts, enrollment state and credential linkage. It is not a `User`, `HouseholdMembership`, assignee, performer or family-order entry. Multiple independently revocable displays are supported by the identity model; no fleet-management features are required.
- Add **`household.display.manage`** to the manager preset. A one-time forward migration grants it to existing holders of `household.member.enroll` only. Do not infer it from Adult, work-management grants or display enrollment. Existing grants/presets otherwise retain their meaning.
- Managers get a focused `/household/displays` destination from Household's secondary management links. List label, setup/access state and friendly last-contact/expiry information. Provide Add display, issue/replace setup code, and Revoke access. Code cancellation is available for an outstanding claim. No rename/delete history workflow or generic permission editor is required.
- Issuance, cancellation, replacement and revocation are household-scoped, Origin/CSRF-protected, version-checked commands with replay identity bound to the actor, target and payload. Replaying a revoke cannot revoke a later replacement session. Configuration versions do not change merely because the display refreshes or updates last-contact time.

### 2. One-time enrollment with recoverable setup

- Issue a random **16-character Base32 code (80 random bits)**, grouped for entry/copy, with a **10-minute** server expiry. Accept case and displayed separators consistently. Only its digest is durable. Show plaintext once in the manager's focused setup view, with expiry, target label, `/display` instructions and Copy. Never place codes or session secrets in URLs, logs, screenshots, local storage or replay payloads.
- One outstanding claim per display. Replacing/cancelling it invalidates the prior claim. Issuing a replacement for an active display keeps its current access working until successful claim; a successful replacement atomically invalidates the old credential and connections. Explicit Revoke immediately invalidates active access and outstanding codes.
- Claim is the only anonymous display auth entry: allowed Origin required, strict schema, bounded rate limit (at most five attempts/minute/source in non-test profiles), and generic invalid/expired/used feedback. No account, password, email or caller-chosen household/permissions is accepted. Validate that the issuing membership is still active and still holds display-management authority at redemption.
- Consumption and new credential creation commit together; concurrent claims have one winner. Rollback cannot consume the code without issuing access. Duplicate manager command IDs must not create extra displays/codes. Since plaintext is not retained, a lost issuance response is recovered by a clear **Generate new code** action, not by inventing a recoverable secret receipt. A lost claim response resolves through session discovery if its cookie arrived, otherwise fresh manager-issued setup.
- Require the enrolling browser to be signed out of human membership access; if it has a valid member session, return an actionable conflict directing use of a separate browser/profile or the existing guarded sign-out flow. Do not silently revoke that person's session or erase their pending outbox during enrollment.
- An already-active display browser can redeem a manager-issued replacement for that same display only. Switching to another display/household requires revocation of its old binding first; entering another household's code must not silently switch an active wall.

### 3. Persistent but bounded display credentials

- Issue a separate 256-bit opaque display session token, store only its digest, and return it only as an HttpOnly cookie. Hosted name **`__Host-hd_display`**, Secure, SameSite Strict, Path `/`, no Domain; local/test name **`hd_dev_display`** uses the existing explicit local/LAN profile. No bearer token in JS storage or query parameters.
- Adopt **90 days inactivity expiry and 365 days absolute expiry** for C-2. Persist the cookie with expiry bounded by the remaining absolute lifetime; successful authenticated HTTP reads refresh last-contact/idle state. Ordinary restart/reload and ongoing daily use must not hit the human 30-day limit. Server expiry/revocation remains authoritative even if a cookie survives. Managers can replace access without creating a new person; expiry recovery uses enrollment.
- Represent the authenticated context explicitly as a display principal, with household/display/session identity and fixed **read-only** scope. Never construct a fake member AuthContext, borrow a manager's grants, accept a payload grant list or modify execution reports to accommodate this slice. C-3 will define execution authority/provenance separately.
- Credential dispatch is explicit by route. Human routes never accept a display credential; display reads never fall back to a human cookie. If both valid credential types are present, active display mode must not inherit the human authority. Detect display mode before mounting the personal App or fetching its data. With active display access, manual navigation to `/plan`, `/household`, login/claim or other personal URLs stays restricted and cannot launch administration. Public health/meta/static content may remain public.
- At `/display`, absent/expired/revoked display access always leads to display setup/unavailable state, never automatic human-session fallback. If a valid human session is discovered there, show only the signed-out-browser guidance needed for setup, not that member's household payload.
- Display responses carry `Cache-Control: no-store`; no service worker or durable household-data cache is introduced. An expired/revoked credential yields an unauthenticated setup/unavailable view without the previous household contents. Browser history/navigation cannot restore authenticated UI after revocation. This is application authorization, not OS/browser kiosk lockdown.

### 4. Dedicated, minimal display reads

Use the following interface boundaries; exact internal types/table organization remain Engineering choices. Every new `/api/v1` route is added to the policy inventory with the correct principal class, and runtime guards enforce it.

| Interface | Allowed caller and result |
| --- | --- |
| `GET/POST /api/v1/displays` | Member with `household.display.manage`: safe list / create named display and issue setup. |
| `POST /api/v1/displays/:displayId/enrollment` and `/enrollment/cancel` | Same manager capability: replace/cancel outstanding setup. |
| `POST /api/v1/displays/:displayId/revoke` | Same manager capability: revoke access and claims for that display. |
| `POST /api/v1/display/claim` | Anonymous, allowed-Origin/rate-limited code redemption; no active human session. |
| `GET /api/v1/display/session` | Active display only: safe device identity, household timezone/date, server time, credential validity metadata. |
| `GET /api/v1/display/dashboard` | Active display only: current household day summaries for both organizations. |
| `GET /api/v1/display/people/:membershipId` | Active display only: same-household friendly identity, current recurring-work summaries and household-visible personal tasks. |
| `GET /api/v1/display/occurrences/:occurrenceId` | Active display only: one permitted occurrence from the current display day, including ordered expected work, source headings and status. |
| `GET /api/v1/display/sync` (WS) | Active display only, allowed Origin: sanitized invalidation and access-loss signaling. |

- Responses are constructed from a field allowlist: friendly names, stable display/person/work identities needed for navigation, family order, household date/timezone/server instant, activity generation, occurrence title/kind/daypart/accountability, domain progress/state and relevant versions. Detail adds only necessary expected step text/order/obligation/source/status and visible personal-task title/owner/status. Do not send birthday, full/contact names beyond the friendly name, email/login/access/grants, claims, audit actor records, raw plans, private task IDs/titles/counts or whole database rows.
- The server determines the display's household and **today**. Arbitrary household/member/occurrence targets, caller-supplied household IDs or historical/future dates cannot widen access. Foreign, private or otherwise unavailable resources fail without disclosing their existence. The manager's human read scope is not reused to implement household-wide display reads.
- Refactor the current household-date materialization core narrowly for use behind separate validated member/display readers. **Read-only describes the device's authority:** a display Today read may perform existing system-owned creation/reconciliation of current unstarted occurrence snapshots, just as personal Today does. It cannot record execution, lock work, edit configuration or materialize arbitrary dates. This is necessary so an unattended wall shows the day before any human opens Today. Reuse the actual resolver; no second approximation of assignment or applicability.
- Obtain a coherent projection of generation/date and snapshots. Preserve stable IDs, routine fan-out, one responsibility per definition/date, optional/Not needed semantics, started variants/survivors, schedule/addition provenance, Unassigned, school filtering and the reset floor. Repeated display reads neither consume turns nor lock work. History remains stored-only and read-only.
- **Personal tasks in C-2:** private tasks are excluded server-side from every display response and event. Household-visible tasks are available in the owner's focused detail, with completed tasks quiet and undated. All existing tasks are treated as **unpromoted**: no personal tasks or their counts contribute to the resting board. C-3 supplies the durable promotion control. Keep authenticated C-1 Household task visibility unchanged.

### 5. A readable wall, with focused inspection

- `/display` is a distinct shell. Default **By person** in saved family order; one simple **By work** alternative. No Today/Plan/Household navigation, Account menu, administrative shortcuts or "complete" checkboxes. Plain status indicators and a quiet read-only explanation make the current slice understandable.
- By person shows all household people, including pending-access people with assigned work, using friendly names. Show recurring-work completion, neutral current state and major unfinished titles/owners as applicable. Zero applicable work means **No assigned work today**, not a fabricated completed checklist. Do not imply hidden/private personal work is included in a person's totals.
- By work shows responsibility rows with accountable names and routine aggregates by definition/date. Preserve person-vs-step count meanings, actual Done versus Not needed and optional-open context. Show Unassigned work prominently in either organization as **Needs assignment** outside any person's count. Empty groups, filtered-empty work, started divergence and ended-but-started survivors follow existing C-1/A/B truth.
- Completed work is quiet; upcoming dayparts compact. Use C-1's bounded daypart relevance and neutral states without introducing clock deadlines. Large households/work lists may use bounded summaries plus a visible **More** count and detail; truncation must not hide unfinished counts or ownership. Do not silently omit a person or unresolved responsibility.
- Tapping a person/work opens a large focused read-only panel. Routine drill-down retains per-person snapshots; responsibility detail retains its composed checklist. Back returns to the origin context; keyboard focus is predictable. After **90 seconds without user interaction**, return from detail to the overview; network traffic does not extend the timer, while touch/keyboard interaction does. Do not interrupt active interaction or auto-open another detail on sync.
- Day of week, friendly date and current hour/minute remain prominent in both organizations and detail. Use the household timezone and server-supplied instant plus elapsed time; browser timezone/clock must not choose the day. Refresh on household midnight and visibility/resume; show a loading transition rather than putting the new date above yesterday's work. No seconds or new time-format preference system.
- Target a **27-inch 3840 x 2160 touch display** with six fictional people, mixed work and no substantial default scrolling. Verify native 3840x2160 CSS pixels and a scaled 1920x1080 viewport at device scale factor 2. Use large typography and restrained density; primary names/date/time must not become ordinary desktop body text. Record computed primary/secondary text sizes and touch-target geometry. Touch targets are at least 48 CSS px; no hover-only controls, horizontal page scrolling or color-only status. Exact layout/fonts are Engineering discretion within Calm Household.
- As an initial geometry floor for the native 4K evidence fixture, primary person names/time use at least **80 CSS px**, and the main work titles/status use at least **48 CSS px**. Equivalent proportional text sizing at 1920x1080 @2x preserves physical scale; retain usable touch targets. These floors make tiny desktop typography a testable failure, but do not replace or guarantee the physical readability judgment.
- Keep manager setup usable at 360px phone width and ordinary desktop. The wall shell must remain usable in a smaller browser window for local evaluation; that does not substitute for 4K/readability evidence.

### 6. Live data, revocation and bounded stale display

- Reuse the household change source but expose a distinct sanitized display channel. Events request a permitted projection refresh; do not forward existing resource IDs/payloads wholesale. Private-only personal-task changes and proposal/access secrets must not appear in display frames. Relevant execution, plans, groups, calendar, family names/order, visible tasks and activity reset invalidate open affected surfaces.
- Authenticate WS upgrades and revalidate before sending display data; track display/session identity to close that device's sockets on revoke/replacement/expiry. Revoke commits durably before closing/sending access-loss signals. Check validity at least every **30 seconds** even when the household is quiet; an open socket does not extend revoked access.
- The client refreshes immediately after relevant events, connect/reconnect and visibility recovery. Coalesce bursts and arbitrate response order for overview and open detail using session identity, request generation, household date and activity generation. Old responses cannot restore revoked data, cleared execution or replaced detail. Revalidate privacy through the server; the client never infers a safe personal scope from stale local data.
- Independently perform an authenticated refresh at least every **30 seconds** while visible to recover missed notifications and validate current access. A display-data read that started before access loss must not bypass final response authorization. On observed revocation/expiry clear all rendered/in-memory household data and reject older in-flight replies immediately.
- During disconnection, a last authorized snapshot may remain in memory for **at most 60 seconds since its last successful authorized refresh**, visibly labeled stale/offline; then blank household data until authorization succeeds. Resume from background checks this deadline before restoring old content. This bounds unattended exposure if the revocation event cannot arrive; it does not promise instant remote erasure of an offline screen. A cold offline reload shows reconnecting, never a persisted household snapshot. Copy must not promise queued execution in this read-only slice.
- A delayed response cannot renew that deadline merely by arriving late: anchor its freshness bound to the request start (monotonic client time) or an equivalent conservative authorization instant, and reject replies outside it. An observed access-loss state also invalidates every earlier request independently of that bound.
- Active-session restart/reload returns to the dashboard without human sign-in. Reset clears execution only and preserves display setup; a newer activity generation invalidates old detail and recovers current permitted work without historical regeneration. No display outbox is created or attached to a member namespace.

## Known risks / assumptions

- Credential lifetime, code lifetime/entropy, idle return and stale-view deadline are explicit Architecture choices for this bounded slice, not claims of an external standard or Product research. Browser storage policies may evict cookies; manager enrollment is the recovery path, with no guarantee against browser data clearing.
- Member-only middleware and current resource-ID broadcasts are real change surfaces. Passing a display as a synthetic manager or hiding sensitive returned fields in CSS violates this brief even when the visible dashboard looks correct.
- Current-day read materialization may write unstarted snapshots; this allowed system behavior is deliberately distinguished from device execution/configuration authority. Do not accidentally promise side-effect-free database reads or regenerate History.
- Normal backups include hashed display access data, as they include human sessions; restoring a backup can restore earlier revocation state. Record that existing operational limitation and manager re-revocation guidance; do not add an external credential service to solve it here.
- The actual screen's readability remains unproven until AT17. The read-only limitation is temporary and explicit; enabling wall completion without C-3's reviewed provenance/authorization would exceed scope.
