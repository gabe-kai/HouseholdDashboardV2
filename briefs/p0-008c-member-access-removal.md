# BRIEF P0-008C - Understandable Member Access and Safe Removal

**Revision:** 1
**Status:** DRAFT — evidence-gated successor; not released for implementation

Architecture must inspect accepted A/B, update the baseline and release this revision for Engineering readiness. Product acceptance is separate. This is one person-management journey; readiness should assess the access/removal integration risk together.

## Why

People currently exists, but authority is chosen through technical enrollment presets, sign-in is token entry, and ordinary departure has no path. Parents need to invite, change access, help with passwords and remove a person without discarding their history or accidentally retaining execution rights. The populated hosted household also needs a provenance-based path to retire sample people while preserving real data.

## Learning question

Can a parent explain a person's role, sign-in status and removal consequences, then perform those changes safely without replacing that person's account or learning the internal grant model?

## Player experience

People lists friendly name, Manager/Member role and neutral sign-in state in saved family order. Person detail separates Profile from Sign-in & permissions. A parent can copy an invitation link/show a QR code, choose understandable access, issue password help, revoke or restore sign-in, and remove a person after seeing affected work. A former person remains identifiable in History; work already started does not silently move to somebody else.

## Behavioral contract

1. **Directory and identity.** Use compact ordered rows showing friendly name, authority role and sign-in status: Not set up, Invitation ready, Invitation expired, Active, Access revoked. Adult/Child stays in Profile and never grants authority. A child without credentials remains assignable and valid. Profile and Sign-in & permissions are read-first sections with explicit editing and visible Back/focus. Former members leave the normal directory/pickers but remain findable from retained history/attention records.
2. **Plain roles over actual grants (D-053).** Offer Manager and Member. New people of either classification default to Member, own routine/responsibility execution, personal-task creation and Approval required for personal routine additions. Members can instead receive Can edit own additions; choose one mode, not both. Manager uses the explicit known management bundle. A secondary Permissions editor describes the closed existing capabilities and the new lifecycle/access/removal capabilities; no arbitrary role/grant creation. Derive role/customized labels from effective grants; preview the exact changes before Save. Do not overwrite legacy/custom grants on upgrade, invitation, password reset, or a cosmetic profile edit. Unknown legacy values remain preserved, non-editable and honestly reported until resolved, never silently dropped.
3. **Administration authority and last manager.** Add `household.access.manage` for permission changes, sign-in revoke/restore and manager-assisted password reset, and `household.member.remove` for removal plus its shared-work impact preview. Backfill these only to existing memberships holding both enrollment and structure authority, retaining other grants. A supplies `household.lifecycle.manage`. Essential manager control is the set enrollment + structure + access.manage + lifecycle.manage; an active, sign-in-enabled user with all four can recover household administration. An ordinary member-administration transaction that would leave zero such managers is rejected before changing access/grants/person data. Pending invitations, unenrolled people, disabled/revoked users and former members do not count. Concurrent self-demotions/removals/revocations must not defeat this invariant. Guide the last manager to invite/promote and activate a successor. A/B's explicitly authorized whole-household reset/restore remain distinct operations with protected owner recovery, not exceptions hidden inside member administration.
4. **Permissions are independent of sign-in links.** Persist/version the person's actual grants even before enrollment. Issuing an invitation never changes them. Claiming reads current grants; it never reapplies a captured preset. Permission saves use expected authority version and bound mutation IDs; verify actor and target again in the commit transaction. Withdraw lost authority promptly, close affected member sockets and rotate/invalidate target sessions under D-007; explain any required sign-in. Preserve same-person identity, assignments, personal ownership and history. A pending invitation may use updated grants if still otherwise authorized, but cannot restore a removed permission; an issuer without current enrollment authority cannot redeem an old issued invitation into access.
5. **Invitation and reset-link lifecycle.** Set up sign-in returns a person-specific Copy link / Show QR code result with household/person name, readable expiry and Cancel. Generate QR locally. Use one-time random 256-bit values stored as digests, invitation expiry 24 hours and password-reset expiry 30 minutes. Apply D-050's fragment exchange, origin, throttle/no-store, no-plaintext-receipts rules. GET/preview does not consume access. Replace cancels prior actionable links of the same purpose; cancel/revoke/removal invalidate them immediately. Authorized preview reveals identity only after token validation. No email-delivery claim. Shared-device redemption explicitly handles the existing signed-in person and pending-work warning; it never silently changes an unrelated account.
6. **Sign-in setup and maintenance.** An invitation recipient chooses Username/Password for the existing membership and lands on their own Today with clear identity; name/household are presented, not recreated. A member changes their own password after supplying the current one. A manager can issue a password-reset link without seeing a password, changing role or creating a person. Successful password change/reset retires prior sessions and outstanding credential-recovery links; self-change may issue a fresh session for that same browser, link reset returns to normal sign-in. Need help signing in? explains manager help and protected owner recovery for the sole manager. Password policy is unchanged; label it Password with helpful inline requirements and password-manager support.
7. **Revoke is not remove.** Revoke sign-in retires active sessions and all outstanding enrollment/password-reset/access-restoration links immediately, with current authority rechecked on consumption. It retains the person, effective permissions, eligibility, personal data and history. Set up sign-in can re-enable that same nondeparted person/user through a fresh authorized link; it cannot bypass last-manager rules or resurrect a removed membership. Ordinary expired sessions may retain queued work under the existing same-identity policy; explicit revoke/removal rejects and retires affected pending intent with an explanation.
8. **Removal preview.** Remove from household is a labeled secondary detail action. Require member.remove, a current target version and recent password proof. One confirmation names the person, affected groups and shared unstarted/upcoming work, distinguishes started work retained as needing attention, and offers an actual next-seven-household-days preview plus links to repair Unassigned plans. Use the authoritative resolver without materialization/turn advancement and keep private task contents/counts out of management summaries. The same resolved sources/versions govern commit; a changed plan/group/target or household-date rollover returns a refreshed preview rather than applying stale consent. Do not require every assignment to be repaired before removal.
9. **Immediate departure eligibility (D-054).** Store departure identity/time and household date separately from sign-in/access state. End sessions/links and exclude the person immediately from every current/future eligibility path: direct routine audience, dated groups (including future versions), fixed/weekly choices, cyclic rings and scheduled-addition ownership. For today/future, reconcile affected existing unstarted rows atomically with departure, versions and receipt. Routines lose the departed person's unstarted participation; fixed/weekly departed responsibility owners and empty rings become explicit Unassigned, while nonempty cycles use the existing dated phase with the departed person filtered out. An addition owner becoming Unassigned cannot fall back to a base owner. Preview, Plan, Today, Household and display agree. Other pending/unlogged-in people remain eligible. Normal group edits still start tomorrow; departure is the explicit immediate exception.
10. **Preserve started work and history.** Never transfer or recompose a started occurrence because its owner departed. Past execution keeps original accountability, actor, performer and device provenance. Show unfinished started work to authorized oversight as Former member / Needs attention with truthful progress; do not add a completion bypass. Both member and display status commands must reject work owned by a departed person, including locked survivors, stale queues and receipt replays. Serialize first action versus departure: action-first preserves a lock and then becomes non-executable; departure-first rejects the action and cannot create a new lock. History stays stored-only. An unused pending person may be physically deleted after exhaustive reference/receipt checks; its mere creation/profile/order or canceled setup receipts must not make every new person permanently undeletable. Retire such solely owned setup artifacts and keep only non-content-bearing replay denial necessary to prevent resurrection. Execution, accountability and shared historical references instead require a former-member tombstone, without blocking ordinary removal. Never reuse removed IDs or let an old create/save receipt resurrect or return a live deleted profile.
11. **Personal and device boundaries.** Departed personal tasks/personalization leave current summaries, proposal inboxes and display projections without ownership transfer or exposing private data. Retain evidence needed by existing history; cancel pending proposals as no-longer-actionable rather than approving for a former member. Invalidate former readers on withdrawal without private IDs/payloads. An enrolled wall remains household-owned if its creator/issuer departs; preserve attribution. Any unconsumed access claim whose issuer has lost authority cannot activate a new display/person. Late responses cannot return departed people/tasks after refresh; reconnect/visibility repair missed notifications.
12. **One-time hosted fixture remediation (D-055).** Add a migration/remediation entry only when canonical fixture IDs exist. Preview the exact canonical origin, current identity/access status and affected shared work; never select by Reed surname. Claimed, renamed or substantively used canonical identities may now be real people and are **not preselected**. Let the manager retain them or explicitly confirm selected records as disposable samples. Batch apply uses the same departure/last-manager/race checks and preserves real neighbors. Remove selected fixtures' exclusively owned disposable personal/setup data together where references prove safe; retain minimal identities and required history/audit where shared or protected. Do not identify a shared routine/group/calendar as sample merely because a fixture person created or used it: the repository has no such provenance. Mixed/unproven work survives with ordinary repair/edit links. If a selected fixture is the last real manager, guide activation of another manager first. D-017's operator cleanup remains its narrow backup-first command; do not loosen it into an indiscriminate delete.
13. **Backup and transition.** Present B's explicit optional backup before batch fixture remediation; never delete samples on migration/startup. The Project Lead may instead choose A/B full reset when the complete dataset is disposable. Populated-through-017 upgrade and rehearsals run on isolated copies; live actions remain the Project Lead's UI choice. Preserve schema and reference inventories, including JSON plan/receipt references, legacy members/sessions, display authorship, personal/proposal and future group records.

## Do not change

- No parental private-task override, arbitrary role creation, social/email auth, Cover/Claim, reassignment of locked work or household portability.
- Revoke sign-in retains household participation; removal ends it. Neither is full reset. Full reset and restore remain A/B operations.
- Used identities must not be destructively cascaded from history. Private personal content never appears in preview/cleanup reports. Household displays are not children of their enrollment manager.

## Acceptance tests

1. **Upgrade and roles:** Through-017 plus accepted A/B populated fixtures preserve all existing/custom grants and identities. New lifecycle/access/removal grants have only the specified backfill. Adult/Child changes do not alter permissions; new people default to Member + approval regardless of classification.
2. **Normal person journey:** Phone/desktop add a person, inspect directory/order/status, edit Profile, inspect permissions, issue Copy link/QR, redeem in another context and reach that person's Today. No new person/duplicate account appears on retries; keyboard/touch/zoom and identity labels are clear.
3. **Permissions:** Manager↔Member, approval↔direct and secondary grant customization update actual access without account replacement. Version conflict retains draft and shows a meaningful diff. Both allow/deny API paths change promptly, including already-open tabs and sockets. Unknown legacy grants are preserved.
4. **Old links:** Issue invitation, change grants, redeem and prove current grants win. Expired/replaced/canceled/revoked links and removed/demoted issuers cannot reinstate authority. Race consume against revoke, permission save and departure; no stale transaction resurrects access. GET/link preview does not consume.
5. **Password help:** Self-change, manager-assisted reset and sole-manager owner recovery preserve membership/grants/work; wrong current password and unauthorized reset fail. New password works, prior sessions and reset links fail, passwords never return to manager/API/logs, and the ordinary sign-in result has the expected identity.
6. **Revoke and restore access:** Revoke an enrolled person with active phone/WS and pending taps; access closes/rejects promptly, profile/assignments/history remain, and a fresh Set up sign-in reuses the same person/user. Distinguish an expired session from deliberate revocation; pending invitations are canceled.
7. **Last manager matrix:** Self/peer removal, revoke and essential-grant loss; a pending invited manager does not count, an active successor does. Race two managers' self-demotions/removals in separate transactions; one essential active manager always survives. Fixture bulk removal uses the same aggregate guard.
8. **Unused/used removal:** Through normal UI add, correct a name and then completely delete a still-unused pending person, despite creation/profile/order receipts; retry its old create/update commands and prove it stays absent. Remove an enrolled person with years-like stored history and JSON/foreign-key references. Used removal succeeds with tombstone, not cascade failure. Check profile order, retained IDs and FK integrity; namesake/foreign targets cannot be removed through ID bypass.
9. **Actual next-week impact:** Normal UI previews/removes direct and group routine participation, fixed Trash, cyclic Cats, Kitchen weekly map and scheduled-addition owner. Verify immediate today/future effects, stable responsibility occurrence ID, ring anchor and Unassigned repair; future group versions cannot re-add the departed member. No preview materialization.
10. **Started/history boundary:** Started routine and responsibility survive with original owner/steps/actor/performer, show needs-attention to manager, and reject all member/display commands for departed owners. Test both first-action/removal race orders. Undo had not unlocked prior work. History is side-effect-free and unchanged.
11. **Live privacy:** Manager/member/two displays with delayed reads see removal and personal-task withdrawal without reload; missed WS delivery recovers on reconnect/visibility. Private IDs/titles/counts stay excluded. Held sharing/status/proposal replies cannot restore departed content; old receipts fail before replay when authority is gone.
12. **Display independence:** Remove a manager who enrolled a wall after another active manager exists. Wall remains enrolled with truthful historical authorship; its unused issuer-bound claims cannot create new access. Departed-owned checklists are not executable at that wall.
13. **Fixture transition:** Mixed real/canonical fixture dataset, renamed and claimed fixtures, same-name nonfixtures, real work created by fixture manager, mixed groups/history/receipts and all-six batch selection. Preview/confirm removes selected disposable sample-owned data, preserves real/unproven content and manager control, and rerun is safe. Backup failure leaves data intact unless the manager explicitly re-confirms without backup. Old narrow CLI cleanup remains safe.
14. **Denials and atomicity:** Per-operation capability matrix, foreign IDs, CSRF/Origin, stale previews, repeated mutation IDs and changed payloads. Inject failures after eligibility/reconcile/access changes; identity, authority, occurrences and receipts roll back together. A stale or mid-hash request cannot commit after actor loss/reset/restore.
15. **Regression and gates:** Exact `validate:pr`/`validate:rc` with selected C phone Chromium/WebKit, desktop geometry, built/Vite invitation/password routes and required Actions aggregate. Recheck D-034 clear, P0-007B phase/Unassigned, C-3A provenance and C-3B privacy. Reports map each subcase honestly; manual Product evaluation remains separate.

## Known risks / assumptions

- The domain contains direct SQL, typed membership references and JSON plan/receipt references; a UI-only tombstone filter is insufficient. Engineering must inventory every read/execute/preview path.
- Canonical fixture origin does not prove current disposability. Ambiguous records are retained by default; shared work has no seeded provenance manifest. This is a real-data preservation rule, not a promise to erase all traces of any Reed identity.
- Access administration plus member departure is the largest P0-008 slice. Its readiness review must verify the shared authority/removal seams; if demonstrated implementation evidence requires decomposition, Architecture retains this complete contract and issues a deliberate revision rather than silently dropping edges.
